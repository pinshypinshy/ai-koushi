# 要件定義書：AI仕様（§5）

[目次へ戻る](../REQUIREMENTS.md)

## 5. AI仕様

### 5.1 呼び出しの全体像

| # | 用途 | タイミング | 出力形式 | 重視する軸 |
|---|---|---|---|---|
| ① | 骨子生成（ステップ分解） | 講義作成時に1回 | 構造化JSON | 精度 |
| ② | 確認テスト生成 | 講義作成時に1回（全ステップ分） | 構造化JSON | 精度 |
| ③ | 講義本文生成 | 各ステップ到達時 | ストリーミングテキスト | レイテンシ |
| ④ | 質問応答 | ユーザー送信時 | ストリーミングテキスト | レイテンシ |
| ⑤ | ステップ要約生成 | ステップ完了時 | 短文テキスト | コスト |

### 5.2 ① 骨子生成

**入力**

- 教材のMarkdown全文
- 講義タイトル（ユーザー入力があれば）

**要件**

| # | 要件 |
|---|---|
| R-1 | 教材を3〜10個のステップに分解する。分量に応じて数を決定する |
| R-2 | 各ステップは前提知識の依存関係を満たす順序で並べる |
| R-3 | 各ステップに、学習目標（そのステップを終えた時点で何ができるようになるか）を1文で付与する |
| R-4 | 各ステップに、教材のどの範囲を扱うかの参照情報（見出しパスまたは行範囲）を付与する |
| R-5 | 教材に存在しない内容をステップとして立てない |
| R-6 | 講義タイトル未入力時は、教材内容から30文字以内のタイトルを生成する |
| R-7 | 数式はLaTeX記法（インラインは `$...$`、ブロックは `$$...$$`）で出力する。Unicode記号やプレーンテキストによる代替表記を用いない |

**出力スキーマ**

```json
{
  "course_title": "string",
  "steps": [
    {
      "order_index": 1,
      "title": "string (30文字以内)",
      "objective": "string (学習目標、1文)",
      "key_points": ["string"],
      "source_ref": "string (見出しパスまたは行範囲)"
    }
  ]
}
```

### 5.3 ② 確認テスト生成

**入力**

- 教材のMarkdown全文
- ①で生成した骨子（全ステップ）

**要件**

| # | 要件 |
|---|---|
| R-1 | 講義全体で10〜30問を生成する。教材の分量とステップ数に応じて決定する |
| R-2 | 各設問は4つの選択肢を持ち、正答はちょうど1つとする |
| R-3 | **ディストラクタ（誤答選択肢）は、教材を理解していなければ誤答しうる水準とする。** 明らかに無関係な選択肢、極端に短い／長い選択肢、「上記すべて」「該当なし」といった形式的な選択肢を含めない |
| R-4 | 選択肢は文体・長さ・粒度を揃える。正解のみが詳細である等の形式的な手がかりを作らない |
| R-5 | 各設問に、なぜその選択肢が正解でありその他が誤りかを説明する解説を付与する |
| R-6 | 全ステップを俯瞰した上で、設問内容の重複を排除する |
| R-8 | 設問はステップに1対1で対応させなくてよい。**複数ステップを組み合わせないと解けない横断設問を全体の2〜3割程度含める**（§4.3.1.1）。残りは単一ステップ設問とし、扱われないステップが生じないようにする |
| R-9 | 各設問に、関連するステップの `order_index` の配列を付与する |
| R-7 | 教材に根拠のない知識を問わない |
| R-10 | 数式はLaTeX記法で出力する（§5.2 R-7 と同一）。問題文・選択肢・解説のいずれにも適用する |

**出力スキーマ**

```json
{
  "questions": [
    {
      "stem": "string (問題文)",
      "choices": ["string", "string", "string", "string"],
      "correct_index": 0,
      "explanation": "string",
      "covered_steps": [1, 3]
    }
  ]
}
```

**検証**：受信後、サーバー側で以下を検証し、違反時は1度だけ再生成する。

- `choices` がちょうど4要素であること
- `correct_index` が 0〜3 であること
- 選択肢に重複がないこと
- `covered_steps` が1つ以上の有効な `order_index` を含むこと
- いずれの設問からも参照されないステップが存在しないこと

**`order_index` は1始まりである。** 2026-08-28 の実測で、`covered_steps` に `0` を含む応答が返り検証に落ちる事象が発生した。出力スキーマの説明とプロンプトの双方に1始まりであることを明示していなかったためで、この1回の再生成に $0.24（当該実行の総額の52%）を要した。**スキーマの説明文で表現できる制約は、検証で弾く前に明示する。** 検証は最後の防波堤であって、再生成のコストは戻らない。

### 5.4 ③ 講義本文生成 ／ ④ 質問応答

**コンテキスト構成**

| 層 | 内容 | 更新頻度 |
|---|---|---|
| システム | 講師としての役割定義、口調、進行ルール | 固定 |
| 教材 | 教材のMarkdown全文 | 講義内で固定（**プロンプトキャッシュ対象**） |
| 骨子 | 全ステップの定義 | 講義内で固定（キャッシュ対象） |
| 進捗 | 完了済みステップの要約（⑤で生成） | ステップ完了ごと |
| 現在地 | 現在のステップ定義 | ステップごと |
| 対話 | 現ステップ内の全メッセージ | 発話ごと |

教材と骨子は講義中不変であり、かつ最大でおよそ8万トークンに達しうるため、プロンプトキャッシュを適用してコストとレイテンシを削減する。これはコスト要件（§8.2）の前提である。

**振る舞い要件**

| # | 要件 |
|---|---|
| R-1 | 一度に提示する情報量を制限する。1発話は概ね400〜800文字とし、長大な解説を一度に出力しない |
| R-2 | 各発話の末尾で理解確認または問いかけを行い、ユーザーの応答を待つ |
| R-3 | 教材に基づいて解説する。教材外の補足を行う場合はその旨を明示する |
| R-4 | 現在のステップの学習目標から逸脱しない。後続ステップの内容は簡潔な言及に留める |
| R-5 | ユーザーの理解が不十分と判断される応答があった場合、別の切り口で言い換える |
| R-6 | コード例や具体例は教材の記述を優先し、必要に応じて補う |
| R-7 | 数式は必ずLaTeX記法（インラインは `$...$`、ブロックは `$$...$$`）で出力する。Unicode記号による代替表記を用いない（§4.1.3のレンダリング対象とするため） |
| R-8 | そのステップが前提とする知識・用語のうち、教材が説明を与えずに用いているものは、最初の発話で名前を挙げ、未習であれば申し出るよう促す。ユーザーの応答から前提の理解が不足していると判断したときは、先へ進まず前提へ遡る（遡る範囲を示して同意を得る）。前提の解説は教材外の補足であり、R-3のとおりその旨を明示し、現在のステップの学習目標に必要な範囲に留める |
| R-9 | 抽象的でイメージが湧きにくい内容を扱うとき、またはユーザーの理解が不十分と判断したときは、身近な例えを用いた説明ができることを提案し、望まれた場合に示す。例えは理解の補助であり教材の定義に取って代わらないため、示した後は教材の記述へ戻し、対応関係とその例えが成り立たない範囲を述べる |
| R-10 | 1発話に含める問いかけ・提案は1つまでとする。R-2の理解確認とR-8・R-9の提案が重なると、ユーザーがどれに答えるべきか決められなくなるため |
| R-11 | 話し言葉に近い敬体で書く。硬い漢語や翻訳調の言い回しを避け、相手へ語りかける表現を交ぜ、一文を短くする。ただし砕けた書き方を許すのは説明の地の文のみで、用語の定義・数式・コード・教材からの引用は正確さを優先する。常体・若者言葉・過剰な感嘆符は用いない。絵文字は段落や項目の先頭で内容の種類（要点・注意・例え・まとめなど）を示す用途に限り、1発話につき2〜3個までとする |

R-8は「既知のものは挙げない」判断を伴うが、後続ステップへ渡るのは⑤の要約だけである。そのため⑤の要約要件に「そのステップで補った前提知識と、ユーザーが既に知っていた前提」を含める。これが無いと、同じ前提を毎ステップ挙げ直すことになる。

R-11を置くのは、文体を指定しないと出力が翻訳調の硬いですます調に寄り、対話ではなく教科書の朗読になるためである。上限（常体の禁止、絵文字の個数）まで書くのは、「馴染みやすく」とだけ指示すると口調の振れが講義ごとに大きくなるためで、対象を説明の地の文に限るのは、平易さと引き換えに定義や数式の正確さを失わせないためである。絵文字を全面的に禁じないのは、段落の先頭で内容の種類を示す用途では可読性に寄与するからだが、文末の感情表現に使うと発話ごとに密度が振れてかえって読みにくくなるため、用途と個数の双方を制限する。

前提知識を①の骨子でステップとして立てる案は採らない。§5.2の「教材に存在しない内容をステップとして立ててはならない」に反し、②が教材に根拠のない設問を作れないこと、進捗率の分母がユーザーごとに変わることと整合しないため、前提は講義中の補足として扱う。

### 5.5 モデル選定

| 用途 | モデル | 理由 |
|---|---|---|
| ① 骨子生成 | `gemini-3.1-pro-preview` | 教材全体の構造把握と依存関係の判断が必要で、失敗コストが最も高い |
| ② 確認テスト生成 | `gemini-3.1-pro-preview` | ディストラクタ品質（§5.3 R-3）が成果物の価値を左右するため |
| ③ 講義本文生成 | `gemini-3.7-flash` | 対話のたびに呼ばれるためレイテンシとコストが支配的 |
| ④ 質問応答 | `gemini-3.7-flash` | 同上 |
| ⑤ ステップ要約 | `gemini-3.7-flash` | 定型的な要約であり上位モデルを充てる必要がない |

**モデルIDは設定値として外出しする。** ①②の出力品質は本アプリの価値を直接左右するため、実際の参考書を用いた比較検証を行い、必要なら上位モデルへ差し替えられる状態にしておく（§11.3.1）。

**Pro 系は preview 版しか存在しない（2026-08-27 時点）。** モデル一覧を確認したところ、`gemini-3.1-pro` は存在せず `gemini-3.1-pro-preview` のみが提供されている。Gemini 3系の Pro はこれ1つで、3.5 / 3.6 / 3.7 は Flash 系のみである。preview は予告なく仕様変更・提供終了がありうるため、モデルIDを設定値として外出しした判断がここで効いている。`gemini-pro-latest` というエイリアスも存在するが、指し先が変わると①②の出力品質が黙って変わるため採用しない。

**思考トークンの扱い。** Gemini 3系は思考トークンを消費し、これは課金上の出力に算入される。実測では、6トークンの出力に対して72トークンの思考が発生した。③④⑤はレイテンシとコストが支配的であるため、思考の水準を明示的に下げる（③④は `LOW`、⑤は `MINIMAL`）。①②は精度を優先するため既定のままとする。

**①②の思考は既定のまま据え置く（確定、2026-08-28）。** 実測では、①②の出力19,642トークンのうち12,745トークン（65%）が思考だった（①78% / ②59%）。講義作成コストの約9割は出力トークンであり、思考の水準を `LOW` に下げれば作成コストはおよそ半減する見込みである。それでも下げないのは、①②の出力品質が本アプリの価値を直接左右する（本節冒頭）ためで、削減幅よりも品質低下の損失が大きいと判断した。この判断を後から見直せるよう、思考トークンは出力トークンの内数として `ai_usage_logs.thinking_tokens` に記録する（§6.3）。

### 5.6 構造化出力

①②はJSONスキーマを指定した構造化出力を用い、パース失敗を構造的に排除する。スキーマ違反時のリトライは§5.3の検証と合わせて最大1回とする。

Gemini API では `responseMimeType: "application/json"` と `responseSchema` を指定する。

### 5.7 エラーハンドリング

| 事象 | 対応 |
|---|---|
| レート制限（429） | 指数バックオフで最大3回リトライ |
| サーバーエラー（5xx） | 同上 |
| コンテキスト長超過 | アップロード時の文字数制限（§4.1.2）で事前に防止する。それでも発生した場合はユーザーに教材の分割を促す |
| スキーマ違反 | 1回再生成。再度失敗時はエラーとして扱う |
| ストリーミング中断 | 部分生成分を保存し、ユーザーに再生成ボタンを提示する。保存した発言には中断の印（`messages.interrupted`）を付け、再読み込みの後も同じ導線を出す。再生成は失敗したときと同じプロンプトを送り直し、成功したら途切れた発言を置き換える。③か④か、履歴をどこまで載せるかはサーバーが発言の並びから決める（Q-33） |
| クォータ超過・支出上限到達 | 課金上限に達した場合、生成は失敗する。ユーザーにその旨を明示する（§8.2.4） |
| 認証エラー（401） | APIキーの失効を意味する。リトライせず即座にエラーとし、管理者（＝本人）へ通知する |

### 5.8 AI呼び出し層の抽象化

**AI呼び出しはインターフェースとして定義する（確定）。** MVPで実装するのは Gemini 版のみであり、抽象化は将来の差し替え余地を確保するためだけに置く。

| メソッド | 入力 | 出力 |
|---|---|---|
| `generateOutline` | 教材Markdown、タイトル候補 | §5.2 のスキーマに適合したオブジェクト |
| `generateQuiz` | 教材Markdown、骨子 | §5.3 のスキーマに適合したオブジェクト |
| `streamLecture` | 講義ID、現ステップ、進捗要約、対話履歴 | テキストの非同期イテレータ |
| `streamAnswer` | 講義ID、現ステップ、質問文、対話履歴 | テキストの非同期イテレータ |
| `summarizeStep` | ステップの対話ログ | 要約テキスト |

**抽象化を置く理由**

| # | 理由 |
|---|---|
| 1 | モデルや呼び出し方式を変えた際の比較検証を、上位のロジックを変えずに行える |
| 2 | 出力品質に不満が出た場合、他社モデル（§11.3.1）へ AI層だけを差し替えられる |

抽象化はインターフェースの定義に留め、実装を1つしか持たない段階で過剰な汎用化を行わない。
