#### Q-21 Google OAuth の実装方式

関連：§7.1

**決定**：`@hono/oauth-providers` ＋ 自前セッションCookie。

`@auth/core` は D1 アダプタが独自のテーブル群を要求し §6.3 と別系統のスキーマが増えるため却下。完全自前実装は `state` 検証を自分で書く分だけ事故る面が増えるため却下。

#### Q-22 `@google/genai` の Workers 上での動作

関連：§7.1

**決定**：動作する（確認済み、2026-08-27）。

バンドル・構造化出力・ストリーミング・コンテキストキャッシュAPIのいずれも利用できた。

#### Q-24 タブバー（B-1）の構成

関連：§3.4

**決定**：教材／講義／確認テストの3タブとし、講義作成はタブから外してオーバーレイ（SC-03）に移す。

タブは「選択中の講義に対するビュー」を切り替える機構であり、新規講義の作成という講義スコープを持たない操作が同居すると軸が2つ混在する。空いた枠には、講義に紐づく教材原文を読み取り専用で表示する教材タブ（SC-16）を置く。

#### Q-25 「骨子は成功したが確認テストだけ失敗」の表現方法

関連：§4.1.6

**決定**：`courses.quiz_status`（`pending` / `ready` / `failed`）を追加する。

status の3値ではこの状態を表せない（`failed` にすると講義タブまで利用不可になり、`ready` にすると失敗した事実が消える）。`status=ready` かつ `phase=quiz` のような組み合わせを規約として使う案は、§6.3 の「ready では phase は NULL」と矛盾するため却下した。逆向き（講義が failed でテストが ready）は②が①の出力を入力に取る以上あり得ないため、制約ではなく実行順序で保証する。

#### Q-26 Googleアカウントを持たない相手への提供手段

関連：§4.6

**決定**：運営が発行するID・パスワードによるゲストサインインを追加する。

講義の作成まで可能とし、上限のみ月2件・$3 に絞る。閲覧だけならサンプル表示（ログイン画面の「画面を見る」）で足りるため、アカウントを発行する以上は実際に使えることに意味がある。上限を分けるのは、§8.2.3 の上限が利用者ごとに数える設計であり、ゲストの人数分だけ費用が積み上がるため。パスワードは PBKDF2-SHA256 で保存する（Workers で使える鍵導出のうち実用に足るのは PBKDF2 のみ）。

#### Q-27 運営用の管理画面

関連：§4.7

**決定**：`/admin` に読み取り専用の運営管理ページを置く。

権限は `users.is_admin` に持たせ、判定はリクエストのたびに DB を参照する（セッションに載せると剥奪が期限まで効かない）。環境変数で管理者を持つ案は、許可リストを D1 へ移した理由（Secrets は読み出せず上書きしかできない）をそのまま再導入するため却下した。段階1で書き込みを持たせないのは、まず「見えること」を確認してから操作を足す方が、壊した場合の切り分けが利くため。ログイン記録（`access_logs`）はこのページのために新設する。

#### Q-28 教材入力欄が Markdown を前提として見えること

関連：§4.1.1

**決定**：ラベルと補助文から Markdown を前面に出す表現を外す。

§4.1.2 は当初からプレーンテキストを許容しているのに、UI が「Markdown を貼り付け」と名乗っていたため、記法を知らない利用者には必須の前提に見えていた。詰まる原因を残したまま §4.8 の説明だけを足すのは順序が逆であり、まず文言で発生自体を減らす。Markdown への言及を補助文に残すのは、記法を知っている利用者には有用な情報であるため。知らなくても使えることは、プレースホルダの文面と §4.8 のガイドが担う。

#### Q-29 使い方が分からず最初の講義作成で止まる利用者への手当て

関連：§4.8

**決定**：定型回答のみの使い方ガイド（SC-17）を置く。AI は呼ばない。

想定される質問は「Markdown とは」「PDF を使いたい」のように答えが一意に定まり、生成する必要が無い。AI を呼ばなければ §8.2.3 の上限と無関係になり、ヘルプでの誤答も起こらない。自由入力を段階1に含めないのは、費用の計上先が未定であること、アプリと無関係な汎用チャットとして使われる余地があること、候補以外に何が聞かれるかを観測する前では AI に答えさせる内容が決まらないことによる（§4.8.3）。PDF は §11.1 のとおり取り込みが未対応であるため、外部の生成AIで Markdown へ変換してもらうプロンプトを配る（§4.8.2）。

#### Q-30 同じ教材でもう一度学び直す手段

関連：§4.5

**決定**：講義の複製を設ける。教材・ステップ分割・確認テストの設問を引き継ぎ、対話ログ・解答記録・進行状況だけを初期化した講義を作る。

骨子（①）と設問（②）を作り直す案は、同じ教材から同じものを生成し直すだけで AI 費用が二重にかかるため却下した。既存講義の進捗をその場でリセットする案も却下した。元の対話と正誤の記録が消え、1周目と2周目を比べられなくなる（`attempts` の履歴は §11.2 の間隔反復・学習統計の前提でもある）。

**月間の講義作成数（§8.2.3）は消費させない**。あの上限は AI 費用を抑えるために置いたものであり、複製は AI を呼ばないためである。一方で月間コストの上限には従わせる（複製した講義を受講すれば③④が動くため）。複製であることは `courses.duplicated_from` に残す。

なお、件数を `courses` の行数で数えると**削除した時点で当月の件数が戻る**ため、「作成 → 複製 → 元を削除」で内容を保ったまま枠だけ空けられ、上限が意味を失う（複製を入れる前から、作って消せば枠が戻る状態ではあった）。そこで数え方を `ai_usage_logs` へ移し、**当月に①骨子生成を行った講義の数**とする。ログは講義を削除しても残るため（FK を張っていない）削除で戻らず、複製は①を呼ばないので自動的に対象外になる。同一講義の2回目以降の `outline`（＝再試行）を数えないよう `course_id` でまとめて `MIN(created_at)` で判定する。代償として、上限に達したときに講義を削除して枠を空けることはできなくなる。

#### Q-31 特定の利用者だけ月間上限を変えたい場合の扱い

関連：§8.2.3

**決定**：`users` に個別上限の列（`course_limit` / `cost_limit_usd`）を設け、NULL を「種別の既定値に従う」とする。

既定値そのものは `server/src/limits.ts` に残し、DB には例外だけを置く。既定値まで DB へ移す案は、上限の出どころが2箇所になり、どちらが効いているかをコードから読めなくなるため却下した。コードに利用者IDの例外表を書く案も却下した。1人増えるたびにデプロイが要り、許可リストを環境変数から D1 へ移した理由（§4.6）をそのまま再導入する。

件数と金額を別の列にするのは、片方だけ緩める場面があるためである。上書きはセッションに載せず毎回 DB を引く。載せると Cookie の期限（30日）まで古い上限が残り、緩めた側・絞った側のどちらにも即座に効かない（`is_admin` を毎回引くのと同じ理由、Q-27）。設定は `npm run limit:set` / `limit:clear` で行い、管理ページ（§4.7）は段階1の読み取り専用のままとする。

#### Q-32 全ステップ完了後に質問できないこと

関連：§4.2.4

**決定**：入力欄を開いたままにし、質問応答（④）だけを受け付ける。発言は最後のステップに紐づける。

完了時点で `courses.current_step_id` を NULL にする設計（§4.2.2）がそのまま「質問もできない」状態を生んでいたが、講義を終えた後こそ残る疑問があり、そのために講義を作り直させるのは §8.2.3 の上限に照らしても釣り合わない。

`current_step_id` を最後のステップへ書き戻す案は却下した。講義が未完了に戻り、完了バナー・確認テストへの誘導・管理ページの完了判定まで巻き戻る。代わりに、文脈を組むときだけ最後のステップへフォールバックする（`loadLectureContext` の `allCompleted`）。`messages.step_id` を NULL 許容にする案も却下した。マイグレーションに加え、ステップ境界の区切り表示と完了ステップの対話ログ閲覧（§4.2.3）が拠り所を失う。

**完了後に③を通さない**のは、終えたはずの解説がもう一度流れて完了表示と食い違うためで、サーバー側で 409 を返す。④のプロンプトからは「後続ステップで扱う」「本筋へ戻す」の指示を外す（完了後は成り立たない）。件数上限は①骨子生成で数えるため増えないが、月間コストと講義単位のトークン上限には従う。

#### Q-33 受講中に③④の生成が途中で失敗した後の扱い

関連：§5.7

**決定**：途切れた発言に印（`messages.interrupted`）を残し、「再生成する」で失敗したときと同じプロンプトを送り直す。成功したら途切れた発言を置き換える。

当初は中断を画面の一時的な状態（`streamError`）にしか持たず、再読み込みや講義の切り替えで再生成の導線が消え、途切れた発言が完了したものとして残っていた。ボタンも「続きを生成する」として③を呼んでおり、④の失敗でも講義本文の続きを指示していた。

途切れた箇所から続けさせる案は却下した。どこで切れたか・出力がどこに表示されるか・どこから書き始めるかを AI に正しく伝える必要があり、コードブロック内で切れた場合などに出力が読めない形で始まるおそれが残る。再生成では既に出力した分をもう一度出力するが、1発話は 400〜800 文字（§5.4）であり、その費用より確実性を取る。

**何をやり直すかはサーバーが決める**（`POST /api/courses/:id/regenerate`、`regeneratePlan`）。最後の発言が回答の無い質問、または直前が質問である途切れた応答なら④、それ以外の途切れた応答なら③とし、履歴はやり直す応答の直前までに切り詰める。クライアントから④を送り直させる案は、質問が二重に保存され履歴も失敗時と変わるため却下した。

途切れた発言は成功するまで残す（読める分を捨てない）。再生成がまた途中で失敗した場合は、届いた分が前回より長いときだけ置き換える。全ステップ完了後は④の再生成だけを受け付ける（Q-32）。「次のステップへ進む」は失敗の表示中も出す（Q-4。隠すと失敗が続く場合に先へ進めない）。既存の発言は印が 0 のままで、過去に途切れたものは見分けられない。
